# 잇룸 (it room) 기획서

> 폐쇄형 IT 소식 커뮤니티. 초대받은 사람만 들어와서 IT 뉴스와 소식을 올리고 읽는 공간.

- 작성일: 2026-09-22
- 버전: v0.1 (초기 버전 기획 확정)
- 스택: Next.js (App Router) + Supabase (Auth, Postgres, Storage) + Vercel

---

## 1. 개요

### 1.1 한 줄 정의
초대된 회원이 IT 소식을 Threads 스타일의 짧은 글로 올리고 함께 읽는 폐쇄형 SNS. 소유자 한 명이 운영한다.

### 1.2 왜 만드는가
- 공개 SNS의 소음 없이, 아는 사람들끼리 IT 소식을 공유하고 싶다.
- 회원 관리는 최소화하고, 글 쓰는 경험(에디터, 이미지, 링크)은 편해야 한다.

### 1.3 참고 서비스
- Threads, X: 피드 형태, 짧은 글, 단일 컬럼 타임라인
- 페이스북: 링크 미리보기 카드
- GeekNews, 각종 블로그: IT 뉴스 큐레이션 성격

### 1.4 "폐쇄적"의 정의
1. 공개 회원가입이 없다. 소유자가 Supabase 대시보드에서 초대 메일을 보내야만 계정이 생긴다.
2. 로그인하지 않으면 어떤 페이지도 볼 수 없다. 루트(`/`) 접근 시 즉시 `/login`으로 보낸다.
3. 검색엔진 색인을 막는다 (`robots: noindex`).

## 2. 사용자와 권한

| 역할 | 설명 | 할 수 있는 것 |
|---|---|---|
| owner | SNS 소유자 (나). 1명 | 읽기, 글 작성, **모든 글** 수정·삭제, 본인 폴더에 이미지 업로드, 모든 이미지 삭제 |
| member | 초대받은 회원 | 읽기, 글 작성, **본인 글만** 수정·삭제, 본인 폴더에 이미지 업로드·삭제 |
| 비로그인 | 아무나 | 로그인 페이지만 접근 가능 |

- 역할은 `profiles.role` 컬럼으로 관리한다. 코드에 이메일을 하드코딩하지 않는다.
- 수정·삭제 권한은 `canManagePost(viewer, authorId)` 하나로 판단한다 (본인 글이거나 owner). DB RLS → 서버 액션 → 페이지 가드 → UI 노출 네 겹 모두 같은 규칙을 쓰고, RLS가 최종 방어선이다.
- 초기 버전에서 member의 상호작용(좋아요, 댓글, 북마크)은 없다.
- 관리자 페이지는 만들지 않는다. 계정 생성은 Supabase 대시보드로 대체한다. 닉네임 변경과 탈퇴는 회원 본인이 `/account`(내 정보)에서 한다.

## 3. 기능 요구사항

### 3.1 인증
- 이메일 + 비밀번호 로그인.
- Supabase Auth 설정에서 **Enable sign ups 를 끈다**. 회원가입 페이지를 만들지 않는다.
- 계정 생성 흐름:
  1. 소유자가 Supabase 대시보드 > Authentication > Users > Invite user 에서 이메일 입력.
  2. 상대가 초대 메일의 링크를 클릭하면 `/auth/callback`으로 돌아와 비밀번호 설정 화면(`/set-password`)으로 이동.
  3. 비밀번호 설정 후 피드로 진입.
- 비밀번호 재설정: 로그인 화면에 "비밀번호를 잊으셨나요?" 링크. Supabase의 reset 메일을 그대로 사용.
- 로그아웃: 상단 헤더 메뉴.
- `auth.users`에 사용자가 생성되면 DB 트리거로 `profiles` 행을 자동 생성한다 (기본 role = member).

### 3.2 접근 제어
- Next.js `proxy.ts`(구 middleware)에서 세션 확인. 세션 없으면 `/login`으로 redirect. 예외 경로: `/login`, `/auth/callback`, `/set-password`, `/reset-password`, 정적 자산.
- 로그인 상태로 `/login` 접근 시 `/`로 redirect.
- DB 레벨에서도 RLS로 이중 방어 (4장 참고). 미들웨어를 뚫어도 데이터는 못 읽는다.
- 글 작성은 로그인한 모든 회원. 수정·삭제는 작성자 본인 또는 owner만 (2장 표). 앱의 검사는 명확한 오류 메시지용이고, 최종 판단은 RLS가 한다.

### 3.3 글 (Post)
- 형태: **Threads/X 스타일**. 제목 없음, 본문만.
- 본문: 위지윅 에디터로 작성한 HTML.
- 태그: 자유 태그, 여러 개. 쉼표 또는 Enter로 추가.
- 링크 미리보기: 본문의 **첫 번째 외부 URL** 하나를 OG 카드로 표시.
- 작성은 모든 회원. 수정/삭제는 작성자 본인 또는 owner.
- 삭제는 hard delete (초기 버전에서는 휴지통 없음). 삭제 전 확인 다이얼로그.

### 3.4 위지윅 에디터
- **Tiptap** 사용 (React 생태계에서 가장 널리 쓰이는 에디터).
- 툴바 구성 (Threads 스타일에 맞춰 최소화):
  - 굵게, 기울임, 취소선
  - 인라인 코드, 코드블록
  - 링크
  - 글머리 목록, 번호 목록
  - 이미지
- 제목(H1~H3), 표, 정렬 등은 넣지 않는다.
- 저장 형식: HTML 문자열. 렌더링 시 서버에서 sanitize 한다.

### 3.5 이미지 업로드
- 저장소: Supabase Storage 버킷 `post-images` (private).
- 업로드 방식 3가지 모두 지원:
  1. 툴바 이미지 버튼 → 파일 선택
  2. 에디터 영역에 드래그 앤 드롭
  3. 클립보드 붙여넣기
- 업로드 즉시 Storage에 올리고, 에디터에 이미지 노드로 삽입.
- 파일 경로: `{user-id}/{uuid}.{ext}`
- 저장 시 본문 HTML에서 `<img>`를 분리해 `posts.images`(경로 배열)에 넣고, 화면에서는 본문 아래 이미지 타일로 렌더링한다 (Threads 구조). 수정 화면에서는 이미지가 본문 끝에 다시 삽입된 상태로 열린다.
- 이미지 URL은 `/media/{경로}` 라우트 핸들러를 거친다. 핸들러가 세션을 확인하고 1시간짜리 signed URL로 redirect 한다. 비로그인은 이미지도 볼 수 없다.
- 제한: 이미지 파일만(jpg, png, gif, webp), 개당 10MB.
- 클라이언트에서 업로드 전 리사이즈(긴 변 2000px)로 용량 절감.
- 읽기는 로그인 사용자만 가능하도록 Storage 정책 설정. 화면에서는 signed URL 또는 인증 세션으로 접근.

### 3.6 링크 미리보기 (OG 카드)
- 글 저장(작성/수정) 시 서버 액션에서 본문의 첫 외부 URL을 추출.
- 서버에서 해당 URL을 fetch 하여 `og:title`, `og:description`, `og:image`를 파싱.
- 결과를 `posts.link_*` 컬럼에 저장. 조회 시 다시 fetch 하지 않는다.
- 실패(타임아웃 5초, 비HTML 응답 등) 시 카드 없이 본문 링크만 남긴다.
- 카드 클릭 시 새 탭으로 열림.

### 3.7 피드
- 경로: `/`
- 최신순 단일 컬럼. 글 카드에 본문 전체, 이미지, OG 카드, 태그, 작성 시각 표시.
- 무한 스크롤 (X/Threads 방식). **전체 글을 한 번에 불러오지 않는다.**
  - 첫 진입 시 서버 컴포넌트가 `FEED_PAGE_SIZE`개만 조회해 렌더링.
  - 스크롤이 바닥 근처(IntersectionObserver)에 닿으면 서버 액션으로 다음 묶음 요청.
  - 커서: 마지막 글의 `(created_at, id)` 쌍. `where (created_at, id) < (cursor_created_at, cursor_id) order by created_at desc, id desc limit N`.
  - 더 이상 글이 없으면 "마지막 글입니다" 표시하고 요청 중단.
  - 태그 필터 상태에서도 같은 커서 방식 유지.
  - `FEED_PAGE_SIZE`는 상수 하나로 관리. 기본값 10, 로컬 검증 시 3으로 낮춰 페이지네이션 동작을 눈으로 확인한다.
- 태그 클릭 → `/?tag={태그명}` 으로 필터된 피드.
- 글쓰기 진입은 헤더의 "쓰기" 탭(모든 폭, 모든 회원)과 홈 피드 맨 위 글 작성칸. 글 작성칸은 `/me`에는 두지 않는다.
- 내 글 모아 보기: `/me`. 로그인한 회원 본인의 글만 같은 커서 방식으로 불러온다. 작성자 ID는 항상 서버 세션에서 정한다.

### 3.8 글 상세
- 경로: `/posts/[id]`
- 피드 카드와 같은 내용을 단독으로 표시. 공유용 고정 URL 역할.
- 작성자 본인과 owner에게만 수정/삭제 메뉴 노출.

---

### 3.9 내 정보 (`/account`)
- 프로필 메뉴의 "내 정보"로 들어간다. 이름, 역할, 본인 이메일을 보여 준다.
- 닉네임 변경: 1~30자, 한글(완성형)·영문 대소문자·숫자만(공백·특수문자·이모지 불가, 0007). 앞뒤 공백은 지운다. 입력 중에 중복·금지어를 확인해 초록(사용 가능)/빨강(불가) 한 줄로 알려 준다. 운영 명칭과 owner 이름은 쓸 수 없고(`guard_display_name`), 대소문자·앞뒤 공백을 무시하고 다른 회원과 겹칠 수 없다(유니크 인덱스). 닉네임은 글을 읽을 때 조인하므로 예전 글에도 바로 반영된다.
- 회원 탈퇴: 비밀번호를 다시 입력받아 확인한다. 본인 이미지 폴더(`post-images/<uid>/`)를 Storage API로 먼저 지우고, `delete_my_account()` RPC가 `auth.users`를 지우면 `profiles → posts`가 cascade로 hard delete된다. 끝나면 로그아웃하고 `/login?deleted=1`로 보낸다.
- owner는 탈퇴할 수 없다(DB 함수, 서버 액션, UI 세 곳에서 막는다).

## 4. 데이터 모델

### 4.1 테이블

```sql
-- 역할 enum
create type user_role as enum ('owner', 'member');

-- 프로필: auth.users 와 1:1
create table profiles (
  id uuid primary key references auth.users(id) on delete cascade,
  display_name text,
  role user_role not null default 'member',
  created_at timestamptz not null default now()
);

-- 글
create table posts (
  id uuid primary key default gen_random_uuid(),
  author_id uuid not null references profiles(id) on delete cascade,
  content_html text not null,
  tags text[] not null default '{}',
  images text[] not null default '{}',   -- Storage 객체 경로 목록. 본문에서 분리해 Threads처럼 본문 아래 타일로 렌더링
  link_url text,
  link_title text,
  link_description text,
  link_image text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

create index posts_created_at_idx on posts (created_at desc, id desc);
create index posts_tags_idx on posts using gin (tags);
```

### 4.2 트리거
- `auth.users` insert 시 `profiles` 행 자동 생성 (role = member).
- `posts` update 시 `updated_at` 자동 갱신.
- owner 지정은 Supabase SQL 편집기에서 한 번만 실행:
  `update profiles set role = 'owner' where id = '<내 uuid>';`

### 4.3 RLS 정책

```sql
alter table profiles enable row level security;
alter table posts enable row level security;

-- 헬퍼: 현재 사용자가 owner 인지
create function is_owner() returns boolean
language sql stable security definer as $$
  select exists (
    select 1 from profiles where id = auth.uid() and role = 'owner'
  );
$$;

-- profiles: 로그인 사용자는 모든 프로필 읽기 가능(작성자 이름 표시용), 본인 것만 수정
create policy "profiles_select" on profiles for select to authenticated using (true);
create policy "profiles_update_self" on profiles for update to authenticated using (id = auth.uid());

-- posts: 로그인 사용자는 읽기와 본인 명의 작성, 수정·삭제는 본인 글 또는 owner (0005)
create policy "posts_select" on posts for select to authenticated using (true);
create policy "posts_insert_own" on posts for insert to authenticated
  with check (author_id = auth.uid());
create policy "posts_update_own_or_owner" on posts for update to authenticated
  using (author_id = auth.uid() or is_owner());
create policy "posts_delete_own_or_owner" on posts for delete to authenticated
  using (author_id = auth.uid() or is_owner());
```

- `posts`의 쓰기는 본문 관련 열만 열려 있다 (0002 열 단위 grant). `author_id`는 insert 때만 쓸 수 있고 수정할 수 없다. `profiles`는 `display_name`만 수정할 수 있어 회원이 `role`을 바꿀 수 없다.

- `anon` 역할에는 아무 정책도 주지 않는다. 비로그인은 DB에서 아무것도 못 읽는다.

### 4.4 Storage 정책 (`post-images` 버킷)
- select: `authenticated` 만
- insert: 본인 폴더(`<user id>/…`)에만. owner도 마찬가지.
- update / delete: 본인 폴더, 또는 `is_owner()` 이면 모든 폴더 (owner가 남의 글을 지울 때 이미지도 정리하기 위해).

```sql
-- 폴더 조건: (storage.foldername(name))[1] = auth.uid()::text
create policy "post_images_insert_own" on storage.objects for insert to authenticated
  with check (bucket_id = 'post-images' and <본인 폴더>);
create policy "post_images_update_own_or_owner" on storage.objects for update to authenticated
  using (bucket_id = 'post-images' and (<본인 폴더> or is_owner()))
  with check (bucket_id = 'post-images' and (<본인 폴더> or is_owner()));
create policy "post_images_delete_own_or_owner" on storage.objects for delete to authenticated
  using (bucket_id = 'post-images' and (<본인 폴더> or is_owner()));
```

## 5. 화면 정의

| 경로 | 이름 | 접근 | 설명 |
|---|---|---|---|
| `/login` | 로그인 | 비로그인 | 이메일, 비밀번호, 로그인 버튼, 비밀번호 찾기 링크. 서비스명 "잇룸" 표시 |
| `/auth/callback` | 인증 콜백 | - | 초대/재설정 메일 링크 처리 후 적절한 페이지로 이동 |
| `/set-password` | 비밀번호 설정 | 초대 링크 경유 | 초대받은 사용자가 최초 비밀번호 설정 |
| `/reset-password` | 비밀번호 재설정 | 재설정 링크 경유 | 새 비밀번호 입력 |
| `/` | 피드 | 로그인 | 타임라인, 무한 스크롤, 태그 필터, 글 작성칸 |
| `/me` | 내 소식 | 로그인 | 본인 글만 최신순, 무한 스크롤, 수정·삭제 메뉴 |
| `/posts/[id]` | 글 상세 | 로그인 | 단일 글, 작성자·owner용 수정/삭제 |
| `/write` | 글쓰기 | 로그인 | Tiptap 에디터, 태그 입력, 게시 버튼 |
| `/posts/[id]/edit` | 글 수정 | 작성자 또는 owner | 기존 내용 로드된 에디터. 권한이 없으면 `/posts/[id]`로 이동 |

### 5.1 공통 레이아웃
- 상단 헤더: 좌측 잇룸 워드마크, 가운데 홈·쓰기 탭(모든 폭), 우측 테마 토글·프로필 메뉴(내 소식, 다크 모드, 로그아웃).
- 본문 최대 폭 640px, 중앙 정렬 단일 컬럼.
- 모바일 우선 반응형.

### 5.2 글 카드 구성 (피드/상세 공통)
1. 작성자 이름 + 상대 시각 (예: "3시간 전"), 수정됐으면 "(수정됨)"
2. 본문 HTML (이미지 포함)
3. OG 카드 (있을 때만): 썸네일, 제목, 설명, 도메인
4. 태그 칩 목록
5. 작성자 본인과 owner 전용: 수정, 삭제 메뉴

- 방향: **구성은 Facebook(상단 헤더, 글 작성칸 카드, 글 카드 목록), 피부는 Mobbin 모노크롬 + 노을 그라데이션 포인트.** 로그인 화면은 노을 하늘 유체 배경.
- 테마: 시스템 설정(`prefers-color-scheme`)을 기본으로 따르고 헤더 토글로 변경. 라이트는 흰 캔버스 + ink #141414, 다크는 같은 사다리를 반전.
- 악센트 블루 #0066ff는 **본문 하이퍼링크 글자색에만** 사용. 버튼, 칩, 포커스 링에는 쓰지 않는다.
- 헤더: 화면 상단 전체 폭 고정 바. 로고 | 홈·쓰기 탭 | 테마·프로필.
- 글쓰기 진입: 헤더의 쓰기 탭과 홈 피드 맨 위 글 작성칸 카드. 모든 회원에게 노출, `/write`로 이동.
- 서체: Pretendard Variable 단일. 제목 650 / 본문 450 / 보조 300 가변 굵기. 코드블록만 JetBrains Mono.
- 컴포넌트: shadcn/ui + Tailwind CSS v4. shadcn 변수는 디자인 시스템 토큰에 매핑.

### 6.1 반응형 (필수)
- 모바일 우선. 모든 화면은 360px 폭에서 깨지지 않아야 한다.
- 브레이크포인트: `sm` 640 / `md` 768 / `lg` 1024.
- 피드 본문 컬럼: 모바일 전체 폭(좌우 16px 여백), `md` 이상 최대 640px 중앙 정렬.
- 헤더(nav 필): 모바일은 전폭에서 좌우 12px 뺀 너비, `md` 이상 640px 중앙. 구성(로고, 홈·쓰기 탭, 아바타)은 동일. 모바일 하위 화면(쓰기, 글 상세·수정, 내 소식)은 "← 제목"을 보이고 탭을 숨긴다.
- 글쓰기 진입: 모든 폭에서 헤더의 쓰기 탭 + 홈 피드 최상단 인라인 행 하나. 플로팅 버튼 없음.
- 에디터 액션 바(취소/게시): 모바일은 하단 sticky, `md` 이상 에디터 아래 인라인.
- 에디터: 모바일에서 툴바가 가로 스크롤되거나 두 줄로 접힘. 키보드 올라와도 툴바가 가려지지 않게 상단 고정.
- 이미지: 컬럼 폭에 맞춰 `max-width: 100%`, 비율 유지. 세로로 긴 이미지는 최대 높이 제한 후 클릭 시 원본.
- OG 카드: 모바일은 썸네일 위, 텍스트 아래 세로 배치. `sm` 이상 썸네일 좌측 가로 배치.
- 검증 기준 뷰포트: 360, 390, 768, 1024, 1440.

## 7. 기술 구성

### 7.1 스택
- Next.js 16 App Router, TypeScript, Tailwind CSS, shadcn/ui
- Supabase: Auth, Postgres, Storage. `@supabase/ssr` 로 서버/클라이언트 세션 공유
- Tiptap (에디터), `sanitize-html` 또는 `isomorphic-dompurify` (렌더링 시 정화)
- OG 파싱: 서버 액션에서 `fetch` + `cheerio`
- 배포: Vercel. Fluid Compute(Node.js) 기본 사용, edge 런타임 사용 안 함
- 개발 중에는 `pnpm dev` 로컬 서버(`http://localhost:3000`)에서 계속 확인하고, Vercel 배포는 기능이 모두 검증된 뒤 마지막에 한 번 한다.

### 7.2 폴더 구조 (예정)
```
app/
  (auth)/login, set-password, reset-password
  auth/callback/route.ts
  (app)/page.tsx            # 피드
  (app)/posts/[id]/page.tsx
  (app)/posts/[id]/edit/page.tsx
  (app)/write/page.tsx
  layout.tsx
components/
  editor/                   # Tiptap 래퍼, 툴바, 이미지 업로드
  post/                     # PostCard, LinkPreview, TagChips
  layout/                   # Header, ThemeToggle
lib/
  supabase/                 # client.ts, server.ts, proxy.ts
  og.ts                     # OG 메타 파싱
  sanitize.ts
supabase/
  migrations/               # SQL 스키마, RLS, 트리거
proxy.ts
docs/
  기획서.md
```

### 7.3 환경 변수
| 이름 | 용도 |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase 프로젝트 URL |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | 공개 anon 키 (RLS로 보호됨) |
| `NEXT_PUBLIC_SITE_URL` | 인증 메일 redirect 기준 URL |

- service role 키는 사용하지 않는다. 모든 쓰기는 RLS를 통과하는 사용자 세션으로 수행한다.

## 10. 개발 워크플로

### 10.1 역할 분담 (Herdr)
- `계획` pane (Claude): 기획, 작업 지시서 작성, 결과 검증, 사용자와 대화.
- `구현` pane (Codex): 작업 지시서를 받아 코드 구현.
- 흐름: Claude가 단계별 지시서를 Codex에 전달 → Codex 구현 완료 → Claude가 로컬 서버와 코드로 검증 → 문제 있으면 수정 지시 → 통과하면 다음 단계.
- 한 단계는 11장 구축 순서의 한 항목 단위로 전달한다.

### 10.2 사용 스킬
- `/frontend-design`: 화면 구현 시 디자인 품질 기준.
- `/ui-ux-pro-max:ui-ux-pro-max`: 반응형, 접근성, 인터랙션 상태, 색/타이포 체크리스트.

### 10.3 계정 및 저장소
- GitHub: 개인 계정, **private repo**. 커밋은 단계 완료마다.
- Supabase: `nnouss` 계정 (GitHub 로그인). 프로젝트 생성 후 URL/anon key를 `.env.local`에 저장. `.env.local`은 커밋하지 않는다.
- Vercel: 배포는 마지막 단계에서 GitHub repo 연결로 진행.

### 10.4 검증 방법
- 로컬 `pnpm dev` 실행 상태에서 브라우저로 확인.
- 반응형은 6.1의 기준 뷰포트 5개에서 확인. 디자인은 `docs/design/디자인-시스템.md` 8장 Do/Don't 기준으로 검토.
- 페이지네이션은 `FEED_PAGE_SIZE=3`으로 낮춰 글 7개 이상 넣고 3 → 3 → 1 → 끝 순서로 로드되는지 확인.
- 권한은 owner 계정과 member 계정 두 개로 로그인해서 확인한다. member는 본인 글에만 메뉴가 보이고 남의 글 수정·삭제가 RLS에서 거부되는지, owner는 모든 글에 메뉴가 보이는지 본다.
